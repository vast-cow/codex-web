# Next host experiment: identify the stream demand gate

For the z170-1 Codex; no SSH access from CFFV5 is assumed. This is a request for a subsequent coordinated experiment, not authorization claimed to have run it. Normal operation has already been restored after `bootstrap-diag-20261117-01`.

The existing trace puts 19.161 seconds between decoded reads and only 20.202 milliseconds inside all 135 data-read promises. Read completion→bridge serialization has a 260-ms median, while serialization and local socket callbacks are fast. Queue cadence matches decoded-read cadence two chunks ahead. Identify the awaited consumer/credit boundary before changing transport parameters.

1. On the host's analysis branch, add opt-in metadata-only spans at the **actual packaged HTTP-service/RPC stream adapter** for `/statsig/bootstrap`, after verifying the loaded bundle and fetch route. Follow the response through its existing body wrapper/TransformStream and RPC readable serializer. The local inspection bundle uses a response wrapper with `body.pipeTo(writable)` and RPC serialization through `createPipe`; these are search anchors, not proof of the host's loaded function names or exact route. Record loaded artifact/hash and the verified call chain. `net.fetch` delegates to the diagnostic fetch implementation; the `net.request`/`Readable.fromWeb` path must be instrumented only if actually used.
2. For every decoded byte range, record monotonic `hostMs`, diagnostic UUID, connection/port/stream identifiers, operation/credit or RPC call ID, sequence, byte count, and cumulative total at:
   - Consumer pull entry; underlying `reader.read()` call/resolution (already present); enqueue before/after, including `desiredSize`.
   - Existing stream sink `write()` entry/return/promise resolution and `writer.ready` or equivalent credit-wait begin/end; record queued bytes/chunks and desiredSize. Preserve the original returned promises.
   - Existing RPC stream-call enqueue, browser acknowledgement/resolve receipt, and the resulting credit release. Trace the actual implicit RPC call/export ID; do not guess its relation to body sequence from time proximity.
   - End-of-stream demand, EOF read, sink close begin/resolution, and final close serialization.
3. Record Node event-loop utilization and `monitorEventLoopDelay` percentiles/max once per second around the same window, alongside existing CPU/RSS. These distinguish an awaited credit from host scheduling pauses. Log only fixed metadata; no application payloads, arbitrary headers, URLs with queries, cookies, or tokens.
4. At the existing upstream transport/decoder boundary, record HTTP version and content encoding plus cumulative **encoded ingress** and **decoded output** timestamps/byte counts and pause/resume or queue-depth signals if accessible without changing consumption. Distinguish observation before versus after a demand gate. If this boundary cannot be hooked without new reads, omit it and explicitly report that upstream production remains unobserved. Do not tee, fully buffer, prefetch, change high-water marks, add read calls, or alter Accept-Encoding merely to obtain timestamps.
5. Use a new capture label and the existing readiness handshake, same authenticated profile/cache and client path, unchanged compression/chunk limits/timeouts. Collect one correlated warm reload only after both sides are ready. Preserve existing diagnostics, clock samples, original fetch UUID and generated diagnostic UUID separately. Retain strict opt-in gating, bounded metadata logging, and restore the normal host diagnostic setting after capture.

Accept the instrumentation only if byte counts, sequence, body, close, and readiness behavior are preserved. Compare logging volume and host resource overhead with the current run. Join upstream and RPC byte ranges rather than assuming equal chunk boundaries.

The decisive check is whether each long inter-read gap is covered by a named unresolved write/credit promise that resolves at a matching browser acknowledgement. If yes, quantify its overlap with transport latency and queued bytes. If gaps occur with credit already available, use event-loop evidence and the verified body-adapter call chain to locate scheduling. If decoded output itself is delayed while demand is pending at a lower boundary, investigate upstream transport/decompression instead. Report any missing boundary rather than assigning the delay to an upstream service.

Only after that result should a single bounded credit/window change be considered, with identical-path before/after captures verifying body/Ready correctness, reduced gaps, bounded memory, CPU, and cancellation behavior. No timeout increase or notification suppression is part of this experiment.
