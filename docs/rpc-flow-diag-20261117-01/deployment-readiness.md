## Final isolated A/B results

The shared-admission matrix held transport and window ceiling constant in both arms. A used a 64 KiB minimum and B used 512 KiB. It covered 20 mixed-IPC application cases and eight private loopback netem cases with two balanced A/B and B/A pairs. The older full-stack result used a smaller body and observed 958.2 MiB. The fresh matrix used the same hard 2 GiB and zero-swap limits. All case assertions passed and only the two deliberately nonreceipting peers stopped. Data tickets, estimated flight and decoded backlog returned to zero. Packet queues drained and the parent qdisc matched before and after. All 45 repository tests passed with Chromium enabled.

| Profile | A decoded MiB/s | B decoded MiB/s | Change |
| --- | ---: | ---: | ---: |
| Packet variable latency | 1.031 | 1.701 | +65.1% |
| Packet 8 Mbit/s | 0.549 | 0.548 | −0.1% |
| Application variable latency | 1.884 | 2.668 | +41.6% |
| Application variable latency with compression | 1.414 | 2.443 | +72.8% |
| Application slow / stalled | 2.284 / 1.609 | 2.297 / 1.620 | +0.5% / +0.7% |

The fresh matrix measured a 506,246 B per-connection upper bound and 1,012,324 B aggregate upper bound for combined data reservations. Estimated flight peaked at 1,836,828 B per stream and 4,460,868 B aggregate. Decoded backlog peaked at 1,114,112 B aggregate. Per-client staging and assembly reached roughly 2.10 MB on each endpoint, parked host bytes reached 163,840 B, native WS buffering reached 396,985 B host and 49,794 B browser, and sampled TCP TX reached 786,604 B. Application cancellation propagated in 2.277 s in A and 2.440 s in B. Disconnect reached the source within 15.1 ms and RPC drain followed close within 5.6 ms. The matrix cgroup peaked at 697.0 MiB with zero limit or OOM events.

**Full-stack charged-memory gate failed.** With the larger response fixture and concurrent webview, the two isolated runs peaked at **1,386.9 MiB** and **1,314.0 MiB**. Both had zero limit and OOM events. The second ran after the matrix and mounted the staged release and dependencies read-only. Its highest 100 ms sample was 1,312.9 MiB during restored A's health phase, with 989.6 MiB anonymous memory, 290.9 MiB file-backed and 29.5 MiB kernel memory. This peak includes Chromium, the helper process and local upstream/TLS relay. It establishes a workload-wide headroom problem under the proposed ceiling and does not attribute the excess to B. The 2 GiB hard limit and 1,280 MiB experiment ceiling were unchanged across attempts. [Per-case metrics, process tree and memory samples](deployment-readiness-evidence.json).

## Acceptance and rollback criteria

Operational invariants apply immediately. In an authorized isolated run, stop upon a breach and preserve metadata. During a future authorized live B arm, stop the batch and restore A upon a breach, unexpected disconnect, lost monitoring, or an invalid readiness check. A planned negative test passes only if the intended fault is isolated, the healthy peer keeps working, and the next operation succeeds.

| Measurement | Operational requirement |
| --- | --- |
| Transport reservations | Shared admission allows 448 KiB issued forward data plus 64 KiB issued reverse data per connection. The 512 KiB combined allowance is the conservative per-connection forward-plus-reverse ceiling. Two admitted connections give 896 KiB strict forward and 1 MiB combined across the process. Priority has a separate 8 KiB per direction per connection and receipts have separate 256 B local headroom. Any exceeded ledger, unexpected admission refusal during the agreed two-client load, premature receipt, or outstanding tickets after teardown fails. A's installed legacy framing has no applicable ticket counter. |
| RPC estimated flight | Keep the bounded candidates' 1,771,040 B adaptive ceiling and 328,192 B maximum estimated atomic charge. Stop bounded runs above 2,099,232 B per stream, including one atomic charge. Require estimated flight to return to zero at terminal drain and no pending credit at quiescence. Record installed A's legacy estimator separately. Estimated bytes are distinct from decoded, native sender and TCP bytes. |
| Encoded staging and retained data | For bounded framing, cap ordinary staged envelopes at 16 MiB and 128 entries, assembly at one 16 MiB envelope, and queued priority charges at 8 KiB per direction and connection. Require host pre-listener and browser app-host receive queues to stay within their 256 KiB and 512 KiB per-port caps respectively, four parked atomic host writers of up to 80 KiB, and split-source backing buffers of at most 1 MiB each and 2 MiB total per connection. Treat overflow, corruption, or unexplained retention after close as a failure. Account for WebSocket and TCP sender bytes independently. |
| Aggregate process memory | Keep the hard cgroup limit at 2 GiB with zero swap allowance. Verify process membership and record `memory.peak` and `memory.events`. Any `max`, `oom`, `oom_kill` or `oom_group_kill` increment or escaped managed child fails. Record local browser and Tailscale charges where they are in separate cgroups. Summed process RSS is diagnostic because it charges shared pages to each process. |
| Cancellation and errors | With an active source, local abort rejects a parked writer and releases its waiter without assigning an operation ID. Remote cancellation must reach the producer, terminate the stream, and leave no reserved operation or orphan producer. A forced source error must reject the reader, and subsequent healthy requests must pass. EOF before an explicit cancellation is insufficient for this check. |
| Reconnection | Allow zero unexpected failed WebSocket upgrades, silent reconnect failures, wrong subprotocols, or reconnect loops after readiness. In a deliberate fault, require a fresh successful upgrade and app IPC once the listener is ready. During legacy/bounded cutover a deliberate new navigation loads the matching preload. |
| Authenticated bootstrap | Every accepted run confirms the approved signed-in account, then a complete successful Statsig response including upstream EOF, exactly-once ordered browser delivery, totals agreeing across the bridge, valid outer and nested JSON, and Ready evaluations. Missing or duplicate segments, unexpected cancellation, fallback initialization, or a lost diagnostic stream fails. The historical byte count is a workload reference. The live payload size can differ with account and flags. |
| Editor readiness | Require primary runtime from the Statsig layer, the explicit route-mounted milestone and an enabled focused editor that accepts and clears an unsent test string. Require the same after the reconnect probe. A successful HTTP response or visible textarea alone is insufficient. |

### Conservative trial values for operator approval

These are proposed limits for the declared workload of two streams per connection and two connections. Approve the thresholds, sampling and actions together before the live trial. The smaller extracted-fixture RSS guards remain valuable for that fixture. The prior full stack's 305.4 MiB Desktop RSS already exceeded the fixture's 256 MiB host RSS guard.

| Measurement | Proposed trial stop or rollback threshold |
| --- | --- |
| RPC flight and decoded backlog | Stop above 4,198,464 estimator bytes per connection or 8,396,928 B aggregate. For actual producer-to-consumer decoded backlog, stop above 512 KiB per stream, 1 MiB per connection, or 2 MiB aggregate. Check event-driven and require zero after drain. |
| Queue alert and drain | Alert if any ordinary sender or assembly holds over 8 MiB or if bytes grow over three consecutive 1 s samples without consumption. Stop upon continued growth for 5 s, zero envelope progress for 15 s, or a non-idle queue 3 s after terminal completion. For bounded connections, stop when native buffering exceeds 512 KiB host or 96 KiB browser per socket. Investigate aggregate TCP TX over 1 MiB for 5 s and roll back if it continues to grow or fails the terminal drain check. Track each layer independently since the same bytes can appear in multiple counters. |
| Memory | Keep the experimental 1,280 MiB whole-stack charged peak ceiling. It was selected before the bootstrap-sized stack rerun against the previous 958.2 MiB peak and leaves 768 MiB below the hard limit. Escalate if a candidate's settled charge is more than 128 MiB above paired A after 30 s on the same process/account workload. Monitor `memory.current` at 100 ms and read `memory.peak` and event deltas. Resolve a 1,280 MiB breach with attributable measurements and operator review before reconsidering the threshold. |
| Cancellation | Source observes application cancellation within 3.0 s of the browser action with earlier 2.10 MB same-direction data in flight. Close-triggered source and RPC cleanup within 250 ms of the client close action in the two-client fixture. The previous 2.38 s peak included ordered bulk ahead of cancellation. Measure on one clock or use bounded timestamps. |
| Reconnect and shutdown | First successful WebSocket and directory IPC within 10 s after listener readiness. No post-readiness failures in any planned cycle. Allow up to 8 s for shutdown and reap before a verified, PID-specific escalation. |
| Account, bootstrap and editor | Account initialization within 15 s of its request. Complete Statsig body and Ready within 30 s of bootstrap request. Primary runtime and usable editor within 60 s of warm navigation or 90 s of cold navigation. Zero failed attempts in one cold plus three warm runs per arm. The prior compressed route milestones were 39.7 s warm and 67.0 s cold. |
| Trial benefit | Require equal correctness and at least 15% lower median matching-body delivery time versus each flanking A on the same client/path. Review an ACK p95 regression above 25%, any queue growth, and any memory increase against route and editor outcomes. An A/A path or workload change invalidates the comparison. |

The current B production-style launcher cannot enforce this monitor contract on its own. The shared-transport server flag emits cumulative peaks at socket close and the launcher only records `rpc-flow` and `bootstrap` messages. Qualify a metadata-only observer for active connections and browser-side queues, bounded clock events and cgroup state before approving the procedure. Keep diagnostic overhead and settings matched where supported. [Transport implementation](../../src/shared/websocket-transport.ts), [server instrumentation](../../src/server/main.ts).

## Production A/B procedure for separate explicit authorization

1. Close the isolated gates first. In an operator-owned staging environment, provision a clean, egress-enabled Codex home and Chromium profile. Have the operator sign in interactively with an approved disposable account. Use separate staging Tailscale state, socket, node identity, host name and service port with equivalent ACLs and TLS forwarding. From the intended client, verify direct or DERP routing and rehearse the actual Codex parent job stop and relaunch primitive. Run the account, bootstrap, runtime, editor, reconnect, error and cancellation gates on staged A and B under the same 2 GiB cgroup and the proposed monitor.
2. Before asking for production authorization, record the maintenance window, client identity, one authorized browser and account, expected tab count, resource/cancellation values, live monitor and on-breach owner. Record the exact approved parent-session relaunch command and placement for both arms. Validate that the effective service cgroup and app-server resource coverage match staging. Keep the original executable, environment, cwd, CLI proxy, Unix socket, A release trees, mode and deployment JSON in a protected operator-owned rollback record. Preserve launch environment in its existing secret store and compare it privately. Verify artifact digests and retain the original A path and dependencies. Stage verified B in a separate path with matched host and compressed browser assets. Keep the production URL and Tailscale configuration fixed.
3. Obtain explicit authorization for production A measurements, diagnostic mode transitions, the two cutovers and restoration. Check that the production PID/start time and serving artifact digest still match the preflight record. Quiesce the app, atomically set `mode` to `diagnostics`, and verify the new A child, same serving artifacts and legacy upgrade. Record one cold readiness check, then one unmeasured warmup and three measured serial warm reloads for A-before. Use the same Chromium binary, authenticated profile, cache policy, client/path and measurement interval in every arm. Record the diagnostics mode and receipt/stream counts for A. Before switching, stop new navigations, wait for active application streams to quiesce and close the test browser.
4. On the authorized parent session, set the private production mode file to `stop` by atomic rename. Wait at most 8 s for both recorded launcher and Desktop child to exit and for the old loopback listener to disappear. If the child already exited, SIGTERM the verified launcher. For a timeout, use the preapproved escalation only after rechecking process start times and release identity. Abort and restore A if any other listener or process ownership is in doubt. Once both recorded processes are gone, atomically install the staged B deployment JSON at the launcher path and the approved diagnostic mode. Launch `/usr/bin/node-22 /tmp/rpc-flow-diag-20261117-01/launcher.cjs` through the approved parent job, with B's `CODEX_WEB_SHARED_TRANSPORT=1` and diagnostic settings. The launcher loads its deployment JSON only at process start.
5. Verify the new PID/start time, real entry point and artifact digests, effective cgroup and socket mappings, TLS document and directory IPC. Navigate afresh to load the matching B preload and verify `codex-ipc-budget-v1`. If the authenticated readiness checks pass, record the cold check, warmup and three measured warm reloads. Collect only metadata for account, ordered body bytes and EOF, Statsig Ready, runtime, editor, diagnostics, connections and resources. Keep the planned cancellation and reconnect probe outside the timed block. Start rollback immediately if any operational gate or approved trial threshold fails.
6. Restore A whether B passes or fails. Quiesce when feasible, stop and reap B through the same verified sequence, atomically restore the original deployment JSON and `normal` mode, and relaunch through the approved parent job with the original environment. Verify A's PID/start time, release digest, port and socket mappings, TLS and legacy upgrade on a fresh navigation, authenticated bootstrap and usable editor. If the acceptance review is still active, repeat step 3's diagnostic transition and cold/warm checks on A-after, then atomically return the launcher to `normal` and verify the new A child and authenticated readiness again. Compare B against both A batches and record final A identity and status.

Use the existing [host readiness relay and comparison protocol](../rpc-window-ab.md) for per-arm authorization, workload controls and evidence fields. The generic capture script records raw WebSocket frames and traces. For this procedure qualify a metadata-only collector, with live stop signals, before production use. The treatment between installed A and B includes both bounded framing and the 512 KiB minimum. The isolated shared-admission A/B comparison holds framing constant and estimates the minimum-window effect.

Use the [private release staging and namespace procedure](shared-websocket.md#reproduction). Copy `docs/bootstrap-diag-20261117-01/chunk-timings.csv` to `control/bootstrap-chunks.csv` alongside the harness. Start the same harness from a shell in a new tmux server selected with `tmux -S STAGE/control/tmux.sock -f /dev/null` inside bubblewrap.
